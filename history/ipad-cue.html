起因

使用者：「iPad 版需要這個往下滑的暗示，才知道要往下滑，因為這個螢幕看起來很大、
好像就卡在這邊。」

第一版（線＋角＋小點，放在照片上）上線一天之後：
「那個往下的暗示很不明顯，放在柱子上，那個角型上還一條線，其實真的完全看不到、
看不出來那個有什麼意思。我覺得這樣做好像不太對，你再想幾個辦法看看。」

一、為什麼看不見（量出來的，這一輪的關鍵）

把指標藏起來，量它**正下方那一塊 44×59** 的背景：

    裝置           最暗    平均    最亮
    iPad 746×977   L* 0    L* 15   L* 45
    iPad Pro 11    L* 0    L*  7   L* 52
    iPad 12.9      L* 0    L*  3   L* 52

**同一塊 44×59 裡，背景從 L* 0（門口那根深色柱子）跳到 L* 52（亮著的門）。**
所以問題不是「亮度不夠」而是**變異太大**：白色的細線落在亮處就不見，
暗暈落在暗處也不見。加上那條線只有 1px、上端還淡出，本來就接近雜訊。

結論是兩條路：
① 不要把記號放在照片上 —— 改放在乾淨的底上（窄帶），或改用版面暗示。
② 一定要放照片上，就要一塊不透明的地，讓背景的變異完全不影響它。

二、落選的做法（都給使用者看過）

第三輪（六案，放在照片上或版面）
    露一角　　第一屏底下露出 44px 的紙色，完全不放記號
    Ⓑ 把手　　小圓角片騎在窄帶上緣
    Ⓒ 圓鈕　　44px 半透明圓（毛玻璃＋細框）＋ 角形
    Ⓓ 字＋角　「往下」兩個小字 ＋ 角形（會多兩個字，屬文案決定）
    Ⓔ 雙角　　兩個加粗角形 ＋ 藥丸底
    Ⓕ 現況　　線＋角＋小點
  → 使用者：「目前的腳型我都不是很喜歡，第一個它的位置在那邊非常突兀。」
     圓鈕特別點名：「圓圈跟現在整個主題都不搭，網站主題是方框導圓。」

第四輪（搬到右下 ＋ 方框導圓）
    Ⓖ 雙角（無框）｜ Ⓗ 框＋單角 ｜ Ⓘ 框＋雙角
  → 使用者：「那個雙角有點靠得太近，而且看起來長度好像不太一樣。」
     「目前是做成方框嗎？我想要跟電腦版一樣是個底色，有套一點顏色上去的底，
       不要有框。」
     ⚠ 長度不一樣的成因：上面那條是 CSS 邊框畫的（13×13 方塊轉 45 度，
       水平跨距 13×√2 ≈ 18.4px），下面那條是 SVG（18px）—— 兩種畫法的尺寸與
       視覺重量本來就不同。使用者一眼看出來。

三、定案

**窄帶右下角、兩條一模一樣的角形 ＋ 套色的底 ＋ 慢速浮動**

位置　貼版心右緣（right: var(--pad)）、垂直對齊「5 個／部定專科」那一列的中線
      —— 實測四個尺寸都是**距窄帶下緣 34.9px**（窄帶的內容不會重排，是常數）
記號　兩條角形都用**同一張 SVG**（data URI）畫，尺寸粗細端點逐像素相同
間距　1.5px　　白　.36　　底　rgba(226,229,230,.10) ＋ --frame-r 的圓角，沒有框線
動　　慢速浮動（translateY 4px、2.4 秒），看 prefers-reduced-motion
觸控目標　44×39.5

⚠ data URI 的 SVG 一定要寫 width/height，只有 viewBox 的話 Safari 當背景圖時
   有時直接不畫（CLAUDE.md 第九節，橫捲提示那一輪踩過同一條）。
⚠ 記號是**裝飾性圖形**，門檻看非文字的 3:1。實測窄帶在記號那一塊是 L* 15.2：

    底            底的 L*   白.68    白.55    白.45    白.36
    無底           15.2     10.6     8.8      7.3      6.1
    淺底 .10       37.0      5.2     4.4      3.8      3.2   ← 定案這一格
    稍濃 .16       44.4      4.1     3.5      3.0      2.6

   **日後若把底換成 .16，白就不能低於 .45**（.36 只剩 2.6:1）。
   底愈濃、白反而愈不明顯 —— 因為底本身把周圍提亮了。
⚠⚠ **點下去的捲動最後改成自己做**（第六輪，上線同一天）。第一版靠 CSS 的
   scroll-behavior: smooth —— 在 Chromium 上逐幀量得到動畫（0 → 32 → 132 → 300
   → 518 → 689 → 891 → 1034 → 1106 → 1118，約 500ms），但使用者拿 iPad 的
   螢幕錄影回報「點下去看起來不是平滑捲動，比較像切換」：
   **iOS Safari 對「點錨點連結」這一種捲動不吃那條 CSS。**
   （那支錄影是 H.264，容器裡的 ffmpeg 與 Chromium 都沒有這個解碼器，
     拆不了幀 —— 這一輪是照使用者的實機觀察改的，不是量出來的。）
   改法：preventDefault ＋ rAF，620ms、ease-in-out cubic。
   ⚠⚠ history.pushState **要在動畫之前推**。放在動畫結束才推的話，瀏覽器記在
      「上一步」那一格的捲動位置已經被更新成目的地，按上一頁只會清掉 hash、
      畫面停在原地（實測）。先推就正確：上一頁回 y=0、下一頁回 1118。
   ⚠ 自己捲之前要把 scroll-behavior 設成 auto，不然瀏覽器會對每一幀再平滑一次
      （頁首那三個標籤用的是同一招）。
   ⚠ 開了「減少動態效果」就整段不接手，交還給原生的瞬間跳轉。

⚠⚠ **浮動那一條刻意不看 prefers-reduced-motion**（第七輪，使用者：「那個角形按鈕
   在 iPad 上沒有慢速浮動」）。iOS 的「減少動態效果」很多人開著，看它就等於這顆
   永遠不動 —— 而「會動」正是它存在的理由（不動的角形使用者已經說過「看不出在
   幹嘛」）。判準和窄帶那個往上數的數字同一條：那個設定針對的是位移／視差／縮放
   這種會讓人不舒服的大動作，原地上下 4px、2.4 秒一次不屬於那一類。
   ⚠ **但點下去的捲動仍然看它** —— 平滑捲動正是它要關掉的東西，兩件事分開處理。

⚠ **點到會亮**（同一輪，使用者：「點到的時候要加變亮效果」）：`:active` ＋ 捲動
   期間掛 `.is-lit`，底 .10 → .24、角形 .36 → .85（＝電腦版 hover 那一階），
   捲完才拿掉，所以整段 620ms 都亮著、不會手一放就暗。
   ⚠ **亮起來要寫在「減少動態」那條 return 之前** —— 第一版寫在後面，
     開了減少動態的人點下去完全沒有反應（實測）。

四、實作上踩到的三個坑

1. **偽元素的舊值要全部歸零。** 正式站的 .hero-cue::before 是那條 1px 的細線
   （有 background 與 border-radius）、::after 是那顆會動的點
   （position:absolute; left:50%; top:6px）。拿它們來畫兩條角形時只清了 background、
   忘了清 position，結果兩條角形**一上一下錯開成階梯**。
2. **keyframes 不能照抄電腦版。** 電腦版那顆是 transform: translateX(-50%)，
   所以它的浮動 keyframes 寫 translate(-50%, 4px)。右下這顆的 transform 是 none，
   照抄會讓它突然往左跳半個身。這裡只寫 translateY。
3. **提案頁的抬頭註解結尾寫成 CSS 的結束記號**（星號＋斜線）而不是 HTML 的 -->，
   註解沒有關起來，把後面整個 header 都吃掉了（querySelector("header") 回 null、
   hero.top 從 0 變 90）。和「CSS 註解裡不能出現註解的結束記號」是同一類的坑。

五、水平位置：往左讓開 28px（第八輪，2026-08-15）

上線之後使用者：「有了。角形的位置太右下，往左一點。」

---- 現況量出來 --------------------------------------------------------
`right: var(--pad)` ＝ 貼齊窄帶內容的右緣，而 --pad 是 clamp(1.25rem, 3vw, 2.5rem)：

    視窗        離螢幕右緣   離「5個／部定專科」字尾
    721x1200    21.6         93.1
    744x1133    22.3         103.9
    746x977     22.4         104.9
    768x1024    23.0         115.2
    820x1180    24.6         139.6
    834x1194    25.0         146.2
    1024x1366   30.7         235.5

**離邊 22~31px 比它自己還窄（44px）** —— 讀起來就是「被擠到角落」，
不是「刻意擺在那裡」。

---- 定案 -------------------------------------------------------------
`right: calc(var(--pad) + 28px)` → 離螢幕右緣 **49.6~58.7px**，
大約是它自己的一個身寬。五階的尺 0／16／28／44／64 給使用者挑，選 28。

⚠⚠ **讓開的量要用定值，不要對齊第三格。** 窄帶的三格是**置中**的、
   版心卻是**滿版**，所以「部定專科」字尾到右緣從 iPad mini 的 104px
   一路到 12.9 吋的 236px，差一倍以上 —— 拿它當錨點，同一條規則在兩台
   iPad 上會差很多。而使用者感覺到的「太右下」是離**螢幕角落**多遠，
   那是離邊的距離，所以用定值。

⚠ **垂直位置一個字都沒動**（距窄帶下緣 34.9px ＝ 三格那一列的中線）。
   使用者只說「往左」。尺寸 44×39.5、慢速浮動、點到會亮、點下去自己 rAF
   捲，全部照舊。

⚠ 七個平板尺寸逐一量過：五階全部留在窄帶內、無橫向捲動。
   最左那一階（64）在最窄的 721 上離「部定專科」字尾仍有 29px ——
   再往左就會開始碰到字，這是這條路的盡頭。
