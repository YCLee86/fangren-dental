這件事在解什麼

首頁「主題與科別」那七顆標記是 .is-filtered-out 純 CSS 隱藏， 網址從頭到尾不變。實測那一節只有 121 個字，整個首頁 2362 字要代表七科， 「口腔外科」全首頁只出現 2 次 —— 所以站上沒有任何一頁接得到「斗六 牙周病治療」。

做法（使用者四輪修正之後定下來的）

① chips 從 <button> 換成 <a> —— 按鈕沒有網址，爬蟲點不下去、AI 引用不了、也分享不出去。
② 那一排同時變成全站的科別導覽列，八頁互連，錨點文字正好是科別名。
③ 著陸頁是 index.html 的快照（使用者：「現在首頁怎麼做的著陸頁就怎麼做，
   只是增加篩選下的科別說明或介紹而已」），搜尋框留著。
④ 別科的文章與醫師是**在產生時真的刪掉**，不是靠 JS 藏起來 ——
   靠 JS 篩的話 Google 抓到的仍是七科全部，繞回原點。
⑤ HERO 拿掉：那張照片與那首詩是全站門面，七頁各放一次會稀釋掉它。

上線當天使用者回報的兩件（同日修掉）

兩件的共同成因是**把提案頁的規矩帶進了正式站**。定案上線時要逐項回頭問：
「這一條是提案頁才需要的，還是正式站也要的？」

⚠⚠ 一、文章卡的瀏覽次數印成一條「—」
    產生器第 9 步原本會把 assets/counter.js 剝掉。那是**提案頁**的規矩
    （CLAUDE.md 第八節：不剝掉的話，每開一次提案頁首頁的計數就多一次）。
    可是這七頁現在是正式站的頁，卡片上的數字是站上的一部分。
  → counter.js 改成**留著**。安全的理由是 HERO 拿掉時 data-views-self 也跟著
    消失了 —— counter.js 只有看到 data-views-self 才會 POST +1，這七頁只剩
    唯讀的 data-views，所以顯示得出數字又不會替任何一篇灌計數。
  → 產生器補了兩條 assert：出現 data-views-self 就 throw、少了 counter.js 也 throw。
    哪天著陸頁又長回窄帶，第一條會擋下來。

⚠ 二、按「全部」回首頁，落在 HERO 上
    那一顆的 href 是 /，所以回到的是首頁最上面那張照片，使用者還要自己再往下
    滑一屏才看得到文章 —— 按了等於沒按。
  → 改成 /#topics（＝「主題與科別」那一排）。頁首那顆「全部文章」本來就指
    #topics，兩者一致。html { scroll-padding-top } 已經處理掉頁首的高度，
    實測落在頁首下方 15px，chips 那一排和第一張文章卡同時在畫面上。
  ⚠ 在首頁上按它會捲到這一排（它自己），那是對的：這一顆的意思一直都是
    「不篩選」，而不篩選的畫面就是首頁。

上線當天第三件：點標籤的「閃跳」（螢幕錄影逐幀拆開）

使用者：「點標籤的時候會有點頁面切換那種閃跳的感覺，跟之前單純在首頁裡篩選的時候
那種很順的切換很不一樣，這個有辦法改善嗎？」

10.7 秒、60fps 的螢幕錄影拆成逐幀比對，量出來是**三件不同的事**（同 CLAUDE.md
第九節第 13 條：「閃」從來不是一件事，修一件不會治好另外兩件）。

⚠⚠ 一、按「全部」回首頁那一跳，是「滑的」，而且 load 之後才開始
    錄影裡 f497（8.28s）整個畫面暗下來（mean 186 → 51），停了 13 幀
    （約 220ms）才到主題與科別。那 13 幀畫的是首頁最上面那一屏：頁首、詩、
    一大片深色（HERO 照片還沒解好）、收尾句、窄帶。
    Playwright 逐幀重現，成因很乾淨：**scrollY 到 DOMContentLoaded 與 load
    都還是 0**，再過約 320ms 才開始動，然後 74 → 296 → 571 → 740 → 768
    滑了約 400ms —— 因為 html { scroll-behavior: smooth }，**瀏覽器連
    「開頁跳到錨點」這一次也照著滑**。
  → 在**解析到標記那一排的當下**就自己捲好，第一幀就在定位
    （改完實測 67ms 起 scrollY 一路都是 768）。
  ⚠⚠ 那一刻文件的高度還不夠捲（只解析到 HERO ＋ 這一節的開頭），scrollIntoView
    會被夾在半路 —— 先把 html 的 min-height 撐到 250svh，load 之後再拿掉
    （那時真正的高度約 11000px，遠大於它）。
  ⚠ 捲之前要把 scroll-behavior 設成 auto，捲完還回去，不然這一次也會變成滑的。
  ⚠ 只在 navigation.type === 'navigate' 時才自己捲：重新整理與上一頁／下一頁
    要交給瀏覽器自己的捲動位置還原。

⚠ 二、著陸頁那排標記，先畫在「還沒捲」的位置，下一幀才跳過去
    錄影 4.7s 那一段看得很清楚：新頁的第一幀，標記列還是從「全部」開始，
    下一幀才捲到「一般牙科・定期檢查」。那支腳本原本在頁尾。
  → 搬到那一排的**正下方**。--topic-pad 那支同理，搬到 </header> 底下 ——
    它決定的是整個 #main 從哪裡開始，晚一步整頁會往下移一次。
  ⚠⚠ 通則：**凡是「決定第一幀長什麼樣」的腳本，就不能放在頁尾那一堆。**
    放在它要影響的那個元素的正下方，解析到就跑，第一幀直接是對的。

三、剩下的那一刀，是「換文件」本身
    標記從 <button> 變成 <a> 之後，那一下就從「同一頁換內容」變成
    「換一份文件」，中間必然有一刀 —— 使用者說的「跟之前在首頁裡篩選很不一樣」
    講的就是這個。
  → @view-transition { navigation: auto; }，.18 秒交叉淡入。
  ⚠ 這是**全站**的：點文章卡、頁尾連結也會淡。不要就把樣式表最前面那一段刪掉。
  ⚠ @view-transition 只能寫在樣式表最外層，不能包在 @media 裡 ——「減少動態效果」
    是靠 ::view-transition-old/new(root) { animation: none } 關掉。
  ⚠ **加了淡入不代表閃跳好了** —— 一和二是位置晚一步才對，淡入只是把硬切變軟。

驗收：首頁 4 個視窗 × 23 個選擇器 × 15 個 computed 屬性 ＋ bbox **0 項有差**；
七頁的一屏量測和上線版逐項相同（perio 661.8／655.5／653.6…）。
