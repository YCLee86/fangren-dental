---- 頁首這一列改用 grid（2026-08-07，第六輪才收斂）------------------------
真機量到的兩個數字，把病因指得很清楚：

  第一次   .brand w = 395.5   （沒有上限，直接撐出視窗 → 頁面可以左右拉 36px）
  第二次   .brand w = 345     （＝ max-width: 100%，被夾住了，但還是佔滿整行
                                → 選單沒位置，只好換行）

兩次都是同一件事：**WebKit 把 `.brand` 這個 flex 項目撐成可用寬度**，
而 Blink 給它內容寬度（131）。`width: max-content` 在 flex 項目上沒有讓 WebKit 改變主意。

所以不再靠 flex 的自動尺寸推論，改用 grid 的軌道明說：

  grid-template-columns: max-content 1fr

**`max-content` 當軌道尺寸是兩邊都實作得很紮實的東西**，
不像「flex 項目 ＋ flex-basis: auto ＋ width: auto」那樣有解讀空間。
左欄就是品牌的內容寬度，右欄吃掉剩下的，選單靠右。

選單自己仍然 flex-wrap: wrap ＋ min-width: 0 ——
萬一右欄真的不夠寬，它在自己的欄位裡換行，不會往外撐。
----------------------------------------------------------------------------
---- 這兩條是頁首寬度失控的真正源頭（2026-08-07 第七輪才抓到）--------------
`<svg>` 如果沒有 width／height 屬性，**它的內在尺寸在 WebKit 是預設的 300×150**。
`.brand-mark` 是 flex 項目、`min-width` 預設 auto ＝ min-content，
於是它縮不到 300px 以下 —— `.brand` 的 max-content 就變成
300 ＋ 間距 ＋ 品牌文字 ≈ 395.5，這正是真機上量到的數字。
Blink 把 `width: 100%` 的 SVG 當成 min-content 0，所以完全看不出問題。

兩條一起補才算收乾淨：
· SVG 補上 width／height 屬性 → 內在尺寸變成 44.29×21.82（CSS 的 width:100% 仍然覆蓋它，
  屬性只是給「內在尺寸」用的）。
· min-width: 0 → 這個 flex 項目不再被 min-content 頂住。
----------------------------------------------------------------------------
**選單一定是一行**（使用者要求）。所以不給 flex-wrap ——
能一行的前提是左欄真的只佔品牌的內容寬度，那件事由上面的
`max-content` 軌道 ＋ .brand-mark 的 min-width: 0 保證。
右欄用 minmax(0, 1fr)：0 是下限，代表這一欄不會反過來把格線撐寬。
只給 left，讓它 shrink-to-fit —— **不要補 right**。
補了之後框會被撐滿，::before 那顆藥丸（inset 的負值）就變成整條全寬。
它的 ::before 確實比自己的框寬 17px（左右各 1.7em），但那 17px 落在
HERO 中間、離頁面右緣還很遠，而且 .hero-stage 的 overflow-x: clip 也收住了。

---- 一個色不夠用的時候（2026-08-07）----------------------------------------
其餘五科的 --accent 一個值就能同時當「字」和「底」，因為它們夠深。
兒牙的黃不行：當底要亮才像黃，當字要深才讀得到，同一個值做不到兩件事。
所以拆成三個，**預設全部等於原本的行為**，其他五科一個像素都不會變：
--accent       當「底」用的階（實心藥丸、按下去的 chip）
--accent-deep  當「字」用的階（線性標籤的字與框）
--on-fill      填色上面的字
＊**這一行必須排在科別色前面。** 它和 [data-spec="kids"] 權重相同，
排在後面會把兒牙的 --accent-deep 蓋回 var(--accent)，黃字就糊在卡上了。
----------------------------------------------------------------------------
兒牙原本是圓凳實測的 --stool #8d5e3a。2026-08-07 換成黃 1a #c28229（十一輪，
推導見 PALETTE.md 第六之二節）。它比其他五科亮，當「字」用會掉出 AA（對卡只有
2.93:1），所以這一科要拆成兩個值 —— 也就是上面 --accent-deep／--on-fill 那組合約。

---- 圓角：比例對齊，不是同一個數字（2026-08-07）-----------------------------
四案裡選了 4「各自往中間靠」：標籤方一階、科別標記圓一階。
但一開始四個標記全寫 8px，看起來就不對 —— 主題與科別的 chip 明顯偏方。
量出來原因很清楚：**圓角要看的是半徑與框高的比例，不是絕對值**。

醫師藥丸（基準）  高 20.86px　8px　　比例 0.384
主題與科別 chip   高 31.00px　8px　　比例 0.258　← 差最多，所以最方
文章標籤          高 22.33px　8px　　比例 0.358
診所資訊標籤      高 23.66px　8px　　比例 0.338

chip 的框本來就比較大（字 13.12px、上下內距各 4px，藥丸只有 0.8px），
同樣 8px 落在大框上就變方了。所以改成**各自取 0.384 × 自己的框高**：

主題與科別 chip 31.00 × 0.384 ＝ 11.9　→ 12px
文章標籤　　　　22.33 × 0.384 ＝  8.6　→ 8.5px
診所資訊標籤　　23.66 × 0.384 ＝  9.1　→ 9px

這樣四個標記的視覺圓度一致，框大小不同也沒關係。
（另一條路是把 chip 的內距縮小、讓框變矮，但那會動到觸控面積，先不動。）

專長標籤維持 6px／比例 0.271 —— 它本來就要比標記方一階，那是選 4 的意思。

---- 科別標記：線條與文字套色，底不套色（2026-08-07 定案）---------------------
醫師藥丸的那套色推廣到另外兩處，都是在標科別的小標籤：
· 主題與科別的五個 chips
· 文章卡上的分類標籤
對應關係寫在 HTML 的 data-spec 上，跟醫師卡共用同一組 --accent，
所以「兒童牙科」在三個地方一定是同一個色，不會各講各的。

色票字疊在卡色 #f4f4f5 上實測 5.03~12.31:1，最低的是兒牙 #8d5e3a 的 5.03。

---- 只有醫師藥丸是實心的（2026-08-07）--------------------------------------
同樣是「科別」兩個字，在瀏覽者心裡不是同一個層級：
· 治療項目與文章的標籤是**分類** —— 站上有哪些科、這篇文章屬於哪一科。

認人的份量比分類重，所以只有它填滿，其餘維持線性。
邊框也給同色（不是透明），框的尺寸才跟線性那三處完全一致。
白字對六個科別色 5.53~13.52:1。

---- 玻璃的深淺（2026-08-07 從電腦版回推）--------------------------------
舊版是「在兩組 rgba 之間內插，終點不透明」。那個框架本身就錯了，
電腦版做到第五輪才看出來，這裡一併換掉：

  · 往不透明的終點內插，條子壓在照片最暗的下半部與窄帶上時反而**變淺**，
    看起來像一塊浮在夜色上的灰板。**玻璃不會這樣。**
  · 正確的模型是：**顏色固定、只有濃度在變**。
    壓在夜色上就深、壓在紙色上就淺 —— 深淺交給底下的東西決定。

現在有兩個各自獨立的捲動進度，而且它們剛好前後相接：
  t  窄帶進入條子 → 條子被窄帶填滿。這一段只調**濃度** .06 → .84。
  u  窄帶開始離開 → 完全離開。這一段把玻璃**換成實色**，
     換過去的那個實色就是 .84 濃度疊在紙色上的合成色（算出來是 #393736），
     所以交接的那一瞬間顏色數值完全相同，看不出切換點。

為什麼過了窄帶就得變實色：只要還留著一點透明度，
底下換成紙色時條子一定會跟著變亮 —— 光把切換點提早沒有用。
------------------------------------------------------------------------
下緣淡出的起點。**只能綁 t，不能綁 u。**
  淡出的那一段和「紙色從下面填進來」是從同一條下緣往上長的，
  綁 u 的話兩者一定重疊 —— 淺色底上那段「由深漸淡」會被讀成一條陰影。
  綁 t³ 是讓淡出在紙色出現**之前**就已經收乾淨（t 走完 u 才開始）。
窄帶裡的瀏覽數：往上數到最終值。
---------------------------------------------------------------------------
1. **捲進畫面才開始跑，而且只跑一次。** 數字在畫面外跑完等於沒發生過 ——
 窄帶就在 HERO 底下，一開站多半已經看得到，所以多數情況是進站就跑。
2. **先量好最終寬度再歸零。** tabular-nums 保證每個數字等寬，但 8,642 比 0
 寬得多，不鎖住的話整列會在跑的時候一路往外推，旁邊的「次瀏覽」跟著漂。
3. **easeOutQuart**：一開始衝得很快，最後幾百在慢慢收。均速跑起來像進度條，
 沒有「跳動」的手感；要的是那個先衝再停的落差。
4. 使用者把系統設定成減少動態時直接寫最終值，不跑動畫。
5. 沒有 JS 的時候數字停在 0 —— 這是這一頁唯一會壞掉的地方，
 正式站由 counter.js 接手時要一併處理（無 JS 就整個隱藏，跟現在的行為一致）。

上線時的接法：counter.js 從 D1 取回真實數字之後呼叫
window.fangrenCountUp(n)，動畫、寬度、無障礙文字都會一起更新。
